## Security

No Critical or High. Nothing traceable turns a share code into code execution
today. The gaps are defence-in-depth around the Lua VM and input-driven DoS.

### S1. Medium: Lua VM has ffi, debug, io, os, loadstring, no budget
- [x] Done 2026-09-24: the VM is now `ALL_SAFE | DEBUG` (no `ffi` at the C
  level); after boot `io.popen`, `os.execute/remove/rename/getenv` are
  stubs returning `nil, msg`, `os.exit` errors, `string.dump` and
  `package.loadlib` are gone, `debug` is pruned to `traceback`.
  `loadstring` stays because PassiveTree.lua reads its bundled tree data
  through it. Every `load_build_xml` runs under an instruction hook with a
  15 s / 768 MB budget (`run_with_budget`; JIT switched off for the
  duration since traces skip hooks). mlua's `set_memory_limit` is not
  available on LuaJIT, so the hook polls `used_memory()` instead.
- Was: `crates/pob-engine/src/lib.rs:239` `Lua::unsafe_new()` loads
  `StdLib::ALL`; `docs/IOS.md:44` confirms `ffi` survives on device. No
  `set_memory_limit`, no `set_hook`.
- Reachability from XML today: none found. Only `loadstring` reachable from
  build data is `ImportTab.lua:789` (`ProcessSiteJSON`), on a network path
  pobios does not use (`account.rs:39` uses `dkjson.decode`). All
  `LoadModule`/`dofile` args are literals. `treeVersion` from XML is validated
  at `Main.lua:328` before any `io.open`.
- Risk: any future upstream change or ModParser bug that evaluates a string is
  full RCE via `ffi.C` (works interpreter-only).
- Fix: after `dofile("HeadlessWrapper.lua")` (lib.rs:296) run
  `ffi=nil; package.loaded.ffi=nil; package.preload.ffi=nil; io.popen=nil;
  os.execute=nil; os.remove=nil; os.rename=nil; os.exit=nil; string.dump=nil`,
  wrap `loadstring`/`load` to error outside `LoadModule`, add
  `lua.set_memory_limit(512 MiB)` and an instruction-count hook around
  `load_build_xml` (lib.rs:390).

### S2. Medium: input-driven DoS on main thread, with crash-loop tail

- [x] Done 2026-09-24: `MAX_XML_BYTES` is 4 MB and applies to the raw path

- [x] Done 2026-09-24: `BuildModel` writes a `lastBuildLoading` sentinel
  before the launch load and clears it after; still set on the next launch

## Hangs and performance

Frame: one LuaJIT state, `!Send`, in a `thread_local! RefCell`
(`crates/pobng-ffi/src/lib.rs:649-662`), main thread only. LuaJIT is
interpreter-only on iOS. Every `Engine` write sets `buildFlag` and runs
`OnFrame`, a full PoB calc. No timing instrumentation exists; the only estimate
in-tree is `ConfigTab.swift:128` ("a quarter second on a Mac"). Assume
0.5 to 1 s per calc on device.

### H-arch. The structural fix
- [x] Done 2026-09-24 (39946a0, 3939632): the engine lives on a `pob-engine`
  thread; every FFI call is a job over a channel, `with()` blocks for the
  reply so the 139 sync methods are unchanged; `with_async` returns a
  future uniffi polls, and import, compare (xml/spec), calc sections,
  support ranking, timeless search/fallback, trade query and node toggle
  have `_async` twins that Swift awaits. `BuildState.tree` is an
  `Arc<Tree>` swapped into a global after each job; the canvas, node
  position and tooltip read that snapshot and never touch the engine.
  Caveat that remains: the queue is FIFO, so a sync read issued while a
  long async job runs waits for it. Views that read the engine in `body`
  (H3) are the ones that can still stall a spinner.

### H1. Tree tap does everything inside draw(in:)
- [x] Partly done 2026-09-24: the canvas records the tap; BuildModel's
  frame hook applies it with `toggle_node_async`, then refreshes, saves and
  wakes the canvas. Still open: `refresh()` is 22 sync calls and `save()`
  is undebounced, both after every tap. Was: `draw_tree` toggles the node during the frame
  (`pobng-ffi/src/lib.rs:1962-1972` → `pob-core/src/build_state.rs:847-854` →
  `pob-engine/src/lib.rs:5742-5782`, full calc), then `reload_tree` re-runs
  the ~800-line `tree()` chunk (`lib.rs:1569-2544`: ~3000 node tables, ~3100
  connectors with 12-segment arcs, converted field by field). Then
  `frameDidDraw` (`PobViewController.swift:272` → `BuildModel.swift:100-109`)
  runs `refresh()` (`:125-155`: 22 FFI calls, ~18 compile-and-eval a chunk;
  `sidebar_stats` walked twice at 130-131) and `save()` (`:363-366`).
- Impact: 0.5 to 1.5 s main-thread block per tap, inside the display link.
- Fix: `draw_tree` only records the click; Swift applies it next runloop turn
  with a busy indicator; dedupe `sidebar_stats`; debounce `save()` (1 s, plus
  on `sceneWillResignActive`).

### Locks and memory
No lock held across anything. `BOOT` Mutex (`lib.rs:197`) spans only
`Engine::new`; `LIVE`, `GENERATION` are atomics. No Rust→Swift callbacks. The
hazard is re-entrancy: `draw_tree` holds `borrow_mut()` for the whole frame
(`pobng-ffi/src/lib.rs:1932-1981`); any `with()` reached from inside the frame
panics with `BorrowMutError`. Nothing does today. No unbounded growth found;
snapshots capped at 10 (`BuildLibrary.swift:136`); timers use `[weak self]`.

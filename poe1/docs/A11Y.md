# Accessibility

The reason this project exists, and the reason it is worth checking rather
than assuming: PoB draws everything through OpenGL and exposes no
accessibility tree at all.

**The consumer here is automation, not only screen readers.** The owner drives
this app with bad-ass-mcp, which addresses controls through the platform
accessibility tree. So the bar is: every control carries a name and a role
that automation can find, not merely that a keyboard user can reach it by
tabbing. Those are different jobs, and the first is both more valuable and
easier to verify — it can be tested with the tool itself.

## State

Verified by reading the live tree back out of the running app.

**Working.** eframe's `accesskit` feature is on by default and is compiled in,
including the macOS backend. The tree is rich and correctly roled:

- `popupbutton "Weapon 1: Foulborn Tulfall, Opal Wand, Unique"` — slot, item
  and rarity in one addressable name, for all 18 equipment slots
- `checkbox "Flask 1 active"` with its checked state
- All nine tabs as `radiobutton`, the active one marked checked
- `popupbutton "Class, Witch"`, `slider "Resize left dock, 18%"`
- Every stat label and value in the dock panels
- Mod annotations, including "(Not supported in PoB yet)"

Clicking a slot by name through the tree opens its dropdown, with no screen
coordinates involved. That round trip is the real test.

**Broken.** Focus enters the Items slot column but will not advance past the
first row. Cause not yet found; two guesses have already been wrong (see
`05efc0a`).

**Fixed since.** Delete buttons are named after what they delete, item rows
and stat rows carry composed names, and the drag handles report as buttons
rather than unknown.

**Rough edge that remains.** A plain `ui.label` still reaches the tree as
`name: "text"` with its content in `value` — that is how egui maps labels, and
the fix per widget is an explicit `widget_info`. Worth doing wherever a label
is something automation would want to find; not worth doing for decoration.
Note `find_elements(name=...)` matches the whole string, not a substring.

## Working on this

- **Read the tree, do not infer it.** `get_tree` and `find_elements` against
  the running app answer in seconds what screenshots and reasoning get wrong.
  Every conclusion in this file came from doing that; several earlier ones,
  drawn from watching focus rings in screenshots, were wrong.
- **Watch out for focus starting in a text field.** Tab inserts a character
  there rather than moving on, which reads as "nothing is reachable". Press
  Escape first.
- **`widget_info` is manual.** egui gives no safety net: a custom widget
  without it is unlabelled in the tree while looking perfect on screen. Any
  new control needs one, and the composed name matters — "Weapon 1: <item>,
  <rarity>" is useful, "button" is not.
